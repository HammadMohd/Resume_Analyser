1. PROJECT OVERVIEW
================================================================================

Resume Analyzer is a production-grade ATS (Applicant Tracking System) simulator
that analyzes resumes against job descriptions, scores them, identifies missing
skills, and provides AI-powered improvement suggestions.

WHAT IT DOES:
- Parses PDF and DOCX resumes into structured JSON
- Extracts contact info, skills, experience, education, projects
- Scores resumes against job descriptions (ATS score 0-100)
- Simulates 5 real ATS platforms (Workday, Greenhouse, Lever, Taleo, iCIMS)
- Analyzes bullet points for metrics, action verbs, readability
- Rewrites weak bullets using Google Gemini AI
- Tailors resumes to specific job descriptions
- Exports ATS-compliant PDF and DOCX files
- Provides a glassmorphic web dashboard

RUN COMMAND:
    $env:DEBUG="true"; fastapi dev backend/main.py

TEST COMMAND:
    python -m pytest tests/ -v

FRONTEND:
    Open http://localhost:8000 in browser (served via FastAPI StaticFiles)

5. BACKEND ARCHITECTURE & INTERNAL CONCEPTS
================================================================================

5.1 LAYERED ARCHITECTURE
--------------------------
The backend follows a 4-layer architecture:

    HTTP Layer (API Routes)
         |
    Service Layer (Business Logic)
         |
    Engine Layer (Domain Logic)
         |
    Data Layer (Schemas + DB)

- HTTP Layer: Thin FastAPI routers. Handle request/response, file uploads,
  error handling. No business logic.

- Service Layer: Orchestrate multiple engines. UploadService coordinates
  ValidationService + StorageService. TailorService coordinates
  JDParser + STARBulletEnhancer.

- Engine Layer: Pure domain logic. ATSScorer, RuleEngine, SkillsExtractor,
  ImpactAnalyzer. No HTTP or database dependencies.

- Data Layer: Pydantic schemas (data contracts) + SQLAlchemy models (persistence).

5.2 PYDANTIC VALIDATION
--------------------------
All data flows through Pydantic models:

    Request -> Pydantic validates input -> Business logic -> Pydantic output

Example:
    class BulletRewriteRequest(BaseModel):
        original: str           # Required
        context: str = ""       # Optional with default
        missing_skills: list[str] = []

    Pydantic automatically:
    - Validates types (str, list, int, float)
    - Applies defaults
    - Serializes/deserializes JSON
    - Generates OpenAPI docs (Swagger UI at /docs)

5.3 ASYNC/AWAIT PATTERN
--------------------------
FastAPI uses async I/O for non-blocking operations:

    @router.post("/analyze")
    async def analyze_resume(
        resume: UploadFile = File(...),
        jd: UploadFile = File(...),
    ):
        # await suspends this coroutine, frees the event loop
        resume_result = await upload_service.upload_resume(resume)
        # Other requests can be handled while we wait

This allows handling hundreds of concurrent requests with a single thread.

5.4 DEPENDENCY INJECTION
--------------------------
FastAPI's Depends() system provides reusable components:

    async def get_db():
        async with async_session() as session:
            yield session

    @router.get("/resumes")
    async def list_resumes(db: AsyncSession = Depends(get_db)):
        # db is automatically injected
        ...

5.5 FILE UPLOAD HANDLING
--------------------------
UploadFile objects are temporary files on disk:

    resume: UploadFile = File(...)
    # resume.filename = "original_name.pdf"
    # resume.content_type = "application/pdf"
    # await resume.read() -> bytes

Pipeline: validate -> store (UUID rename) -> parse -> extract

5.6 CUSTOM EXCEPTION HIERARCHY
---------------------------------
    AppError (base)
    ├── FileValidationError (422) - Invalid file format
    ├── FileStorageError (500) - Disk write failure
    ├── FileTooLargeError (413) - Exceeds size limit
    ├── FileEmptyError (422) - Empty file uploaded
    └── UnsupportedFileTypeError (422) - Wrong extension

Each has a to_dict() method for structured JSON error responses.

2. STAR ENHANCEMENT (backend/llm/star_rewriter.py:72-74)
   Prompt: "Rewrite using STAR methodology (Situation, Task, Action, Result)..."
   Output: {"star_bullet": "...", "quantified_metric_added": true, ...}

3. BULLET EXAMPLES (backend/services/validation_enhancer.py:174-176)
   Prompt: "Rewrite exactly 5 bullets into improved versions..."
   Output: [{"original": "...", "improved": "..."}, ...]
   Used by: POST /api/v1/resumes/validate

PROMPT BUILDING:
    - Specific role assignment ("You are a professional resume writer")
    - Clear rules (start with action verb, include metrics, no fabrication)
    - JSON output format requirement
    - Context injection (job title, missing skills)

VALIDATION:
    - Regex extracts JSON from response (may have markdown code blocks)
    - Pydantic validates output schema
    - Custom validator checks for hallucinations (no new technologies added)

FALLBACK:
    - If Gemini API fails or unavailable
    - Rule-based logic applies improvements:
      * Stronger action verbs
      * Trimming long bullets
      * Basic structure improvements
    - Lower confidence scores (0.3-0.4 vs 0.8-0.95 for LLM)

10. ATS SCORING ALGORITHM
================================================================================

WEIGHTED FORMULA:
    ATS Score = (Skills × 0.35) + (Experience × 0.25) + (Projects × 0.15)
              + (Education × 0.10) + (Structure × 0.10) + (Formatting × 0.05)

SKILLS SCORING (35%):
    - Required skill matched: +10 points each
    - Preferred skill matched: +5 points each
    - Normalized to 0-100

EXPERIENCE SCORING (25%):
    - Years requirement met: +60 points
    - Level requirement met (entry/mid/senior): +40 points
    - Bonus for exceeding: +10 points

PROJECTS SCORING (15%):
    - 3+ projects: 80 points
    - 1-2 projects: 50 points
    - 0 projects: 0 points
    - Bonus for JD-relevant projects: +10 each

EDUCATION SCORING (10%):
    - Has education entries: 80 points
    - Field matches JD: 100 points
    - No education: 20 points

STRUCTURE SCORING (10%):
    - Checks 5 sections: contact, summary, experience, skills, education
    - Score = (present / total) × 100

FORMATTING SCORING (5%):
    - Average bullet length 40-200 chars: good
    - Too short (<40): -20 points
    - Too long (>200): -10 points

GRADE CALCULATION:
    A: 90+    B: 80-89    C: 70-79    D: 60-69    F: <60

11. PARSING PIPELINE (PDF/DOCX)
================================================================================

UNIFIED ENTRY: ResumeParser.parse(file_path, filename)
    |
    ├── PDF? -> PDFParser
    |   ├── Primary: PDFPlumber (text blocks + coordinates)
    |   └── Fallback: PyMuPDF (page.get_links() for hyperlinks)
    |
    ├── DOCX? -> DOCXParser
    |   ├── python-docx for paragraphs
    |   └── Hyperlink extraction from relationships
    |
    └── Other? -> OCRParser
        └── Tesseract (pytesseract + Pillow)

SECTION DETECTION (SectionDetector):
    - Compiles regex patterns for each section type
    - Scans line-by-line through parsed text
    - Returns list of {type, title, start, end} dicts
    - Handles: contact, summary, experience, education, skills, projects,
      certifications, awards, publications, languages, interests

STRUCTURED PARSING (StructuredParser):
    - Uses section boundaries to extract section text
    - _parse_contact(): NER extraction (email, phone, LinkedIn, GitHub)
    - _parse_experience(): Company, title, dates, bullets
    - _parse_education(): Institution, degree, dates
    - _parse_skills(): Category: skill1, skill2 format
    - _parse_projects(): Name + description + bullets

SKILLS EXTRACTION (SkillsExtractor):
    - 500+ skills in SKILL_DATABASE (dict of category -> skills)
    - ALL_SKILLS: flat list of all skill names
    - Regex patterns: \bskill_name\b (case-insensitive)
    - Proficiency detection: "expert in X", "proficient with Y"


================================================================================
12. SKILLS EXTRACTION ENGINE
================================================================================

SKILL DATABASE STRUCTURE:
    SKILL_DATABASE = {
        "languages": ["python", "java", "javascript", "sql", ...],
        "frameworks": ["fastapi", "django", "flask", "react", ...],
        "cloud": ["aws", "azure", "gcp", "sagemaker", ...],
        "ml": ["machine learning", "deep learning", "pytorch", ...],
        "devops": ["docker", "kubernetes", "jenkins", "ci/cd", ...],
        "databases": ["postgresql", "mysql", "mongodb", ...],
        ...
    }

EXTRACTION PROCESS:
    1. Text is lowercased
    2. For each skill in ALL_SKILLS:
       - Compile regex: \bskill_name\b
       - Search in text
       - If found: add to results with category and confidence
    3. Proficiency detection via context keywords
    4. Deduplication

SKILL MATCHING (for ATS scoring):
    - Resume skills: extracted from resume text
    - JD skills: extracted from JD text (required/preferred)
    - Match: exact lowercase string comparison
    - Missing: JD skill not in resume skills


================================================================================
13. SEARCH & MATCHING (BM25 + EMBEDDINGS)
================================================================================

HYBRID SEARCH (backend/search/hybrid_search.py):
    Final Score = (BM25 × 0.6) + (Embedding × 0.4)

BM25 SEARCH (backend/search/bm25_search.py):
    - Term frequency-inverse document frequency
    - Fast, exact-match focused
    - Good for keyword-heavy matching
    - Returns: score, matched_terms, term_scores

EMBEDDING SEARCH (backend/search/embedding_search.py):
    - Primary: sentence-transformers (all-MiniLM-L6-v2)
    - Fallback: TF-IDF vectorizer (scikit-learn)
    - Cosine similarity between resume and JD vectors
    - Captures synonyms and semantic meaning
    - Returns: score, embedding dimensions

SKILL MATCHING:
    - Extracts skills from both resume and JD
    - categorizes as: matching, missing, extra
    - Returns SkillMatch objects with match_type

WHY HYBRID?
    - BM25 alone misses synonyms ("ML" vs "machine learning")
    - Embeddings alone miss exact keyword requirements
    - Combined gives best of both worlds

14. RULE ENGINE
================================================================================

RULE CATEGORIES:

1. CONTACT RULES (contact_rules.py):
    - Email present: 30 points
    - Phone present: 30 points
    - LinkedIn present: 25 points
    - GitHub present: 15 points

2. SECTION RULES (section_rules.py):
    - Experience section: 35 points
    - Skills section: 30 points
    - Education section: 25 points
    - Summary section: 10 points

20. KEY DESIGN DECISIONS & TRADEOFFS
================================================================================

1. VANILLA JS vs REACT:
    Decision: Vanilla JS
    Why: No build tools, no npm, instant loading, simpler deployment
    Tradeoff: More manual DOM manipulation, no component reuse

2. PYDANTIC vs MARSHMALLOW:
    Decision: Pydantic v2
    Why: Native FastAPI integration, faster validation, better DX
    Tradeoff: Tighter coupling to FastAPI ecosystem

3. REGEX NER vs SPACY:
    Decision: Regex-based
    Why: No model download, faster startup, deterministic results
    Tradeoff: Less accurate for complex entities, harder to maintain

4. GEMINI vs OPENAI:
    Decision: Gemini (free tier)
    Why: No cost for development, good quality responses
    Tradeoff: Less ecosystem support, deprecated library

5. SQLITE vs POSTGRESQL:
    Decision: SQLite (dev) / PostgreSQL (prod)
    Why: Zero-config for development, production-ready for deploy
    Tradeoff: Async SQLite limitations, migration complexity

6. IN-MEMORY RATE LIMITING:
    Decision: Custom in-memory per-IP
    Why: No Redis dependency for basic rate limiting
    Tradeoff: Lost on restart, not distributed

7. STATIC FILES VIA FASTAPI:
    Decision: Mount frontend/ as StaticFiles
    Why: Single server, no CORS, simpler deployment
    Tradeoff: No frontend build pipeline, no hot reload

8. SKILL DATABASE AS PYTHON DICT:
    Decision: Hardcoded 500+ skills in Python
    Why: Fast lookup, no external DB query, deterministic
    Tradeoff: Requires code change to add skills, no learning

22.3 TECHNICAL DEEP DIVE (5 minutes)
---------------------------------------

Q: "Walk me through the architecture."

"The backend follows a 4-layer architecture:

LAYER 1 - HTTP LAYER: FastAPI routers handle requests. Each endpoint is thin -
just validation and response formatting. No business logic here.

LAYER 2 - SERVICE LAYER: Orchestrate multiple engines. For example,
UploadService coordinates ValidationService (check file type/size) and
StorageService (save with UUID filename).

LAYER 3 - ENGINE LAYER: Pure domain logic. ATSScorer calculates scores,
SkillsExtractor matches skills against a 500+ skill database, ImpactAnalyzer
checks bullet quality. These have zero HTTP or database dependencies.

LAYER 4 - DATA LAYER: Pydantic schemas define data contracts. SQLAlchemy
models handle persistence. Async database with PostgreSQL."

Q: "How does the skills extraction work?"

"We maintain a SKILL_DATABASE - a Python dictionary mapping categories to
skills: languages, frameworks, cloud services, ML tools, DevOps, etc.
500+ skills total.

When processing a resume, we compile regex patterns for each skill:
\\bskill_name\\b (case-insensitive). Then scan the text line by line.
If found, we record the skill with its category and confidence score.

For job descriptions, we extract skills from 'Must have skills:' lines
AND scan the full description text. We distinguish required vs preferred
skills based on pattern matching."

Q: "How does the ATS scoring work?"

"It's a weighted formula:
  Skills (35%): Required skill matched = +10pts, Preferred = +5pts
  Experience (25%): Years met = +60pts, Level met = +40pts
  Projects (15%): 3+ projects = 80pts, JD-relevant = bonus
  Education (10%): Has education = 80pts, Field matches = 100pts
  Structure (10%): Checks 5 sections present
  Formatting (5%): Bullet length 40-200 chars

For Multi-ATS simulation, each platform has different rules:
  Workday: Strict header matching, penalizes non-standard formatting
  Greenhouse: Skill-experience context matching
  Lever: Chronological order importance
  Taleo: Exact string matching, bullet compliance
  iCIMS: Degree hierarchy, keyword density"

Q: "How does the Gemini integration work?"

"Three call sites:

1. BULLET REWRITE: User submits weak bullet. We build a prompt:
   'You are a professional resume writer. Rewrite this bullet...'
   with rules (start with action verb, include metrics, no fabrication).
   Gemini returns JSON: {improved, changes_made, confidence}.

2. STAR ENHANCEMENT: Transforms bullets into Situation-Task-Action-Result
   format. Prompt includes target skill and job context.

3. VALIDATION EXAMPLES: Generates 5 improved bullet examples from the
   user's resume. Falls back to rule-based generation if LLM unavailable.

All outputs go through a Validator that checks for hallucinations -
no new technologies added, no fake metrics, length within bounds."

Q: "How do you handle error cases?"

"Each layer has fallback mechanisms:
  - PDF parsing: PDFPlumber primary, PyMuPDF fallback, OCR last resort
  - LLM calls: Gemini primary, rule-based fallback
  - Database: SQLite for dev, PostgreSQL for prod
  - Skills: Exact match primary, partial match fallback

Custom exception hierarchy: AppError -> FileValidationError,
FileStorageError, FileTooLargeError, FileEmptyError,
UnsupportedFileTypeError. Each has structured to_dict() for JSON responses."

"THREE MAJOR CHALLENGES:
